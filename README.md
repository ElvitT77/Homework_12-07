# Homework_12-07

## Задание 1

Опишите основные преимущества использования масштабирования методами:

    активный master-сервер и пассивный репликационный slave-сервер;
    master-сервер и несколько slave-серверов;

Дайте ответ в свободной форме.

### Решение:

1. Активный master‑сервер и пассивный репликационный slave‑сервер

    Большое количество копий данных – благодаря репликации данные дублируются на slave‑сервере.

    Отказоустойчивость – «Если головной сервер выходит из строя, любой другой сможет его заменить». Пассивный slave готов взять на себя роль master’а при сбое.

    Простота применения – «Наиболее распространённый паттерн применения – отказоустойчивость».
   
Такой подход увеличивает производительность без снижения отказоустойчивости. Пассивный slave не создаёт дополнительной нагрузки на master при чтении (если не используется для отчётности), что сохраняет предсказуемость работы основного сервера.

3. Master‑сервер и несколько slave‑серверов

    Ещё больше копий данных – чем больше slave‑серверов, тем выше надёжность хранения данных (слайд 16: «Большое количество копий данных»).

    Повышенная отказоустойчивость – выход из строя одного или даже двух slave не приводит к потере данных и не останавливает систему, так как остаются другие реплики.

    Масштабирование чтения – несколько slave могут параллельно обслуживать запросы на чтение, что реализует принцип горизонтального масштабирования 

    Гибкость – можно выделить одного slave под аналитику, другого – под резервное копирование, третьего – для балансировки пользовательских запросов.

У репликации есть недостатки – расссинхронизация и задержки при передаче данных. При использовании нескольких slave эти задержки могут суммироваться, но преимущества в виде масштабируемости и отказоустойчивости обычно перевешивают.

## Задание 2

Разработайте план для выполнения горизонтального и вертикального шаринга базы данных. База данных состоит из трёх таблиц:

    пользователи,
    книги,
    магазины (столбцы произвольно).

Опишите принципы построения системы и их разграничение или разбивку между базами данных.

Пришлите блоксхему, где и что будет располагаться. Опишите, в каких режимах будут работать сервера.

Состав таблиц (произвольные столбцы):

    users (id, login, email, password_hash, registered_at, last_login, is_active)

    books (id, title, author, isbn, price, store_id, stock_quantity, published_year)

    stores (id, name, address, city, phone, manager_id)

Принципы:

    Вертикальный шардинг – разные таблицы физически размещаются на разных серверах (кластерах). Это позволяет оптимизировать ресурсы под тип нагрузки: пользователи – много авторизаций (запись/чтение), магазины – справочные данные (редкое изменение), книги – смешанная высокая нагрузка.

    Горизонтальный шардинг – таблица books дополнительно разбивается на несколько шардов по ключу store_id (или по id книги). Каждый шард содержит одинаковую структуру таблицы books, но разные диапазоны данных. Это реализует масштабирование записи и чтения.

Разбивка между базами данных:

    База данных A (сервер A) – таблица users полностью (вертикальный шард).

    База данных B (сервер B) – таблица stores полностью (вертикальный шард).

    База данных C (кластер из трёх серверов C1, C2, C3) – горизонтальные шарды таблицы books:

        Шард C1: книги для магазинов с store_id от 1 до 100

        Шард C2: store_id от 101 до 200

        Шард C3: store_id от 201 до 300

Таблицы users и stores не шардируются горизонтально, так как их объём предполагается небольшим или допустимо вертикальное масштабирование. При росте их размера можно применить аналогичное горизонтальное шардирование (например, по id пользователя).

Распределение серверов и режимы работы
| Сервер (или кластер) | Содержимое | Режим работы |
|----------------------|------------|--------------|
| Server A	| users (полная таблица) | Master (принимает все операции записи/чтения) |
| Server B | stores (полная таблица) | Master (запись/чтение) |
| Server C1	| books, шард 1 (store_id 1-100) | Master (запись/чтение для своего шарда) |
| Server C2	| books, шард 2 (store_id 101-200) | Master (запись/чтение) |
| Server C3	| books, шард 3 (store_id 201-300) | Master (запись/чтение) |

Если требуется высокая доступность и масштабирование чтения, к каждому master’у добавляются slave‑реплики (например, Server A_slave, Server B_slave, C1_slave, C2_slave, C3_slave) в режиме асинхронной или синхронной репликации. Чтение с них распределяется балансировщиком.

Принцип разграничения:

    Пользователи и магазины – независимые сущности, поэтому вертикальное разделение на отдельные master‑серверы.

    Книги – привязаны к магазинам (store_id). Горизонтальный шардинг по store_id позволяет распределить данные книг по нескольким серверам, чтобы каждая запись о книге хранилась в одном шарде, а запросы «показать все книги магазина» попадали только в нужный шард (если магазин целиком лежит в диапазоне одного шарда) или во все шарды (если книги одного магазина могут быть в разных шардах – тогда нужен дополнительный уровень агрегации).

Рекомендации по режимам:

    Все серверы со шардами книг работают в режиме master для записи (каждый отвечает за свой диапазон).

    Приложение или маршрутизатор (например, ProxySQL, ShardingSphere) определяет, в какой шард направлять INSERT/UPDATE/ DELETE на основе значения store_id.

    Для чтения возможно использовать как master’ы, так и их реплики – в зависимости от требований к актуальности данных.

    Для таблиц users и stores, если нагрузка на чтение велика, добавляются slave‑реплики, а master остаётся единственным для записи (режим «один master – несколько slave»).
